# Контент: безопасный календарь сезонов

## Что реализовано

`SeasonFeature` — отдельный серверный модуль с реальными переходами по серверному времени:

1. Куратор сохраняет начало сезона: `/season schedule <id> <ГГГГ-ММ-ДД> <причина>`.
2. Начало в 00:00 **Europe/Moscow**, срок ровно **два календарных месяца**, а не 60 дней.
3. `SCHEDULED → ACTIVE → FINAL_WEEK` (за 7 дней до конца).
4. В конце — `FINALIZING`; через 24 часа — `ARCHIVED`.
5. `/season cancel <id> <причина>` отменяет только ещё не начавшееся расписание; история остаётся.

`/season` открывает русское меню (консоли — текст). `/season history` показывает сохранённый календарь всех сезонов. Создание и отмена доступны только `api.staff(source,"owner")`; проверка повторяется внутри обработчика команды. Идентификатор — 3–32 ASCII-символа `[a-z0-9_-]`, причина — 8–160 символов без управляющих/цветовых кодов. Начало разрешено от 5 минут до 366 дней в будущем. Новый сезон разрешён только после отмены/архивации предыдущего.

Окончание сезона **не останавливает другие модули**. FINALIZING — календарное окно для персонала, НЕ автоматический расчёт рейтингов. ARCHIVED означает архив календаря, НЕ архив БД/мира. Ни один путь не удаляет/очищает мир, данные, деньги, инвентари, территории или репутацию, не выдаёт деньги/предметы и не начинает следующий сезон автоматически.

## Точные точки интеграции для родительской ветки

В `CoreRuntime.initialize()`, рядом с остальными вызовами `load`, добавить:

```java
load("ru.warland.season.SeasonFeature", false);
```

Имеющийся `Feature`-контракт уже передаёт `initialize(api)`, `serverStarted(server)`, `tick(server)`, `stopped()`. Новые API, SQL-таблицы, mixin, зависимости и изменения manifest НЕ требуются. Объект должен быть зарегистрирован **один раз**, до регистрации команд. Не создавать несколько писателей одного namespace. По желанию добавить кнопку главного меню, выполняющую `/season` от имени игрока; привилегированные команды через GUI не вызываются.

Изменений `CoreRuntime`, `WarLand`, API, общего Store, build/manifest, `BuildingService` и `BuildingSiteRules` в этой ветке нет. Без подключения указанного hook код компилируется, но команды и таймер не включены.

## Долговечность и ограничения

- Отдельный документ `season / state.v1` через существующие `getState`/`setState`; схема 1, строгие record-инварианты, неизменяемые коллекции, монотонная ревизия.
- Максимум **32** записи за всё время; до 5 переходов на запись; **128 000 символов** JSON; **одна** незавершённая запись, без неограниченной очереди. При заполнении архив не обрезается: новые планы отклоняются до отдельной согласованной миграции.
- На серверном потоке раз в 20 тиков проверяются сроки. Без изменений запись не выполняется. Все пропущенные во время простоя переходы фиксируются одной записью, в истории — исходный срок и фактическое время наблюдения.
- Исправление часов назад не откатывает фазы и не открывает отменённые/архивные идентификаторы. Большой скачок часов вперёд может завершить календарь раньше реального времени; синхронизация времени — обязанность эксплуатации. Данные мира от этого не меняются.
- JSON не публикуется в памяти до успешного завершения `setState`; I/O-ошибка блокирует календарь до перезапуска/перечитывания. Никакого автоматического восстановления пустым документом при повреждении. Отсутствующий ключ (`null`) означает первый запуск, пустая строка — ошибка.
- Повтор идентичного расписания не создаёт запись заново, в том числе после неоднозначной записи и перезапуска. Конфликт параметров того же ID отклоняется.
- Остановленный модуль не выполняет callbacks. Долговечная запись, успевшая завершиться при остановке, читается следующим запуском.
- Уведомления и общий `api.audit` — best effort **после** сохранения. Автор/причина и история переходов находятся в самом атомарном документе. Падение после commit до сообщения может потерять сообщение, но не фазу; `/season` — источник текущего статуса. При восстановлении пропущенных фаз публикуется только последняя, без шквала старых анонсов.

## Проверка

Новые JUnit-тесты `SeasonRulesTest`, `SeasonStoreTest` покрывают сроки, московский календарь/високосный год, пропущенные фазы, откат часов, дубликаты, отмену на границе начала, лимит архива, невозможность менять коллекции, повреждённые/будущие схемы, переполнение ревизии, задержку acknowledgement, занятый writer, отказ I/O, потерянный callback, повтор после перезапуска, остановку и сбой уведомления.

Сборка и тесты выполняются только в отдельном worktree пользователем `warland-build` под общей блокировкой build.lock; результаты и SHA приводятся в PR. Производственные серверы, БД, миры, порты и режим авторизации в этой работе не изменяются.

## Честные release gates

Это работающий безопасный **календарный lifecycle**, не завершение всей спецификации README:

- Рейтинги государств/экономики/событий/игроков, заморозка расчётных снимков и зал славы ещё не подключены.
- Косметические титулы и значки, двухмесячные награды и escrow не реализованы; денежных/предметных наград нет.
- Вайп отсутствует намеренно. Нужны отдельный одобренный runbook, резервные копии БД/мира, доказанный restore и явное операторское подтверждение; этот модуль никогда их не запускает.
- В существующем content остаётся серверно наблюдаемый субботний маршрут с репутацией. Четыре полноценных типа крупных событий (PvE/PvP/экономика/политика), участие/масштабирование/anti-collusion и аварийное завершение ещё требуют реализации и приёмки.
- Сюжетные квестовые цепочки, reroll и конфликтующие фракции не входят в данный срез.
- Нужны интеграционный headless/client smoke после подключения hook, многопользовательская бета 10/20/30 и эксплуатационные clock/restore проверки. Unit/build не являются доказательством live-проверки или готовности сезона к публичному запуску.
