# Backup: честный результат и восстановление состояния сервиса

Задача [#22](https://github.com/ProkStudio/WarLand/issues/22), агент `agent-002-stability-20260906-135209`. База: `e162219e4d137e2828fd04731427164fc33019fe`. Это узкое исправление эксплуатационного инструмента, **не production backup, не проверка восстановления игровых данных и не готовый релиз**. Общие условия выпуска остаются в [#15](https://github.com/ProkStudio/WarLand/issues/15).

## Воспроизведённая ошибка

Исходный `tools/backup.sh` (Git blob `d1450de9dda5ace650b6954501bab441ea9c16ba`) подавлял неуспех `systemctl start` успешным `echo` в EXIT trap. Архив создавался, печаталось `Verified archive`, код процесса был 0, хотя возврат первоначально активного сервиса не удался.

Кроме того, ненулевой ответ `is-active` трактовался как остановленный сервис. Ошибка запроса состояния до/после stop могла позволить архивирование с неизвестным состоянием. Три отдельные регрессии действительно получили код 0 на исходном скрипте и упали. Это synthetic systemctl-сценарии, не утверждение об аварии рабочего сервера.

## Изменённое поведение

- Внутри прежнего эксклюзивного flock читается явный `ActiveState`. Начальные состояния допускаются только `active` и `inactive`; ошибка запроса, пустой ответ, `failed`, переходные/неизвестные состояния отклоняются до stop.
- После stop требуется успешно прочитанный `inactive`. Иначе tar не запускается.
- Для первоначально активного сервиса EXIT trap пытается выполнить start и проверяет `active`, в том числе после ошибки stop, tar, проверки архива, SHA256, INT/TERM.
- Первоначально неактивный сервис скрипт никогда не запускает.
- Если единственная ошибка — невозможность подтвердить recovery, результат **5**, а не 0. Первоначальный ненулевой код backup сохраняется при одновременной ошибке recovery; выводится отдельное предупреждение.
- Финальное `Verified archive` выводится только после успешной проверки архива/записи checksum и требуемого восстановления сервиса. Это не проверка готовности Minecraft к игре.
- Существующие whitelist сервиса, сопоставление WorkingDirectory, внешняя папка backup, flock, umask077, исключения tar и запрет автоматического удаления сохранены. Нет новых dependencies, переменных окружения для production override или изменений runtime/config/schema.

## Использование и отказ

Обычный интерфейс не изменился:

```bash
sudo bash tools/backup.sh /opt/warland/runtime /opt/warland/backups warland.service
```

**Не запускать эту команду как smoke-тест.** Она действительно останавливает согласованный сервис. До реального запуска прочитать Coordination #12, проверить CLAIM/LOCK/активные сессии, согласовать окно, убедиться в доступе для восстановления и наличии места. Не обходить неизвестное состояние сервиса и не менять auth/feature flags ради успешного backup.

Основные коды:

- 0: архив прошёл tar-проверку, checksum записан, восстановление ранее активного сервиса подтверждено снимком `active`.
- 2: ошибочные аргументы/права/сервис/runtime.
- 3: backup lock занят.
- 4: состояние неизвестно/неподходящее, stop не подтверждён или коллизия имени.
- 5: архив подготовлен, но восстановление сервиса не подтверждено.
- Другой ненулевой код: сохраняется ошибка внешней команды; INT/TERM дают 130/143.

При любом ненулевом результате не заявлять успешный backup/recovery и не повторять операцию вслепую. Проверить фактическое состояние сервиса и согласованный путь архивов, сохранить `.partial`, архивы и диагностику, уведомить других агентов. Ошибка start не удаляет полезный архив. При ошибке checksum файл checksum может быть неполным: такой архив нельзя считать прошедшим полный цикл до отдельной проверки.

## Фактическая проверка

Локальная sandbox, непривилегированный пользователь, Bash + Python3.13:

```bash
bash -n tools/backup.sh
PYTHONPATH=tools python3 -m unittest discover -s tools/tests -p test_backup.py -v
```

Результат: **26/26 PASS**, без пропусков; Bash syntax PASS. Покрыты active/inactive, все границы state queries, stop/start failure, tar create/list failure, checksum failure, приоритет исходной ошибки, INT/TERM, busy flock, nonroot/неверный сервис/WorkingDirectory, коллизия архива, staging, сохранность synthetic source, SHA256 и private modes.

Тесты выполняют реальный tar/gzip/SHA256/flock в новых временных каталогах. `systemctl`, `id`, `date` — обязательные заглушки в ограниченном PATH; настоящий systemctl не вызывается. Inherited shell configuration не передаётся. В одноразовой копии скрипта заменяется **только** `/var/lock/warland-backup.lock` на собственный temporary lock; остальной Bash выполняется дословно. Root, Java, VPS, настоящий мир или данные игроков не нужны. Existing CI автоматически обнаруживает новый test-файл; результат CI конкретного PR head необходимо проверять отдельно.

Первый запуск harness был ошибочным: отсутствовал gzip в ограниченном PATH. Он сохранён как ошибка тестовой среды и не считается воспроизведением дефекта. После добавления реального gzip повторная red-серия дала именно три ложных code0, затем unchanged tests против исправленного кода прошли. В конце добавлены четыре проверки сигналов/дополнительных отказов и повторена вся серия.

## Ограничения и откат

`active` — моментальный статус systemd, не readiness/log/gameplay acceptance и не гарантия, что сервис не упадёт позже. Скрипт не может остановить независимых writers/администратора; нужен эксклюзивный операционный доступ. SIGKILL, падение ОС, повторные сигналы в recovery, зависание внешних команд и потеря питания не дают гарантии выполнения EXIT trap. Таймауты start/stop определяет unit; отдельно проверить их до maintenance.

Не менялись snapshot format, restore_snapshot.py, ссылки/внешние mount points, архивные лимиты или race-hardening файловой системы. Сам tar listing не доказывает полноту/восстанавливаемость runtime. Нужен новый изолированный restore, SQLite integrity и запуск копии по эксплуатационному runbook; реальные backup/restore и сохранность всех рабочих данных этой задачей **не приняты**.

Никакой рабочий сервис, мир, БД, секрет, конфиг или backup этой задачей не менялся. Перезапуск для применения изменения исходников не требуется. Откат — обычный revert согласованного коммита, без force-push; он возвращает известный дефект ложного успеха, поэтому не предпочтителен исправлению. Не откатывать и не удалять данные игроков/чужие ветки.
